Let the Scan module answer “is a Scan running?” for every view

Strong in-process
  • App/ViewModels/ScanState.cs (IsRunning :93, Started / StatusChanged / Ended)
  • App/Views/ScanSidePane.cs (_scanning :19, ctor flag :30, SetScanning :110, rule :120)
  • App/Tabs/ScannerTab.cs (SwitchTo :202, OnStarted / OnEnded, _selectable, _scanningText, _usingStage, _tree! :55)
  • App/Tabs/MainTabs.cs :36–47 (“Nothing else holds the module”)
  • App/AppSession.cs · App/Views/DowngraderWindow.cs, ArchivePatcherWindow.cs (Open)
  • tests/…/App/ScannerTabTests.cs, ScanStateTests.cs

Before: one fact, five copies

#134: three fixes to the pushed copies in one day (efdc1cb, a9dd3bd, 150a429).

After: the session holds the Scan module

Problem

“A Scan is running” lives in ScanState, but the tab copies it into five places in two modules. No other window can reach the module, so #131 has nowhere to land.

Solution

The session holds ScanState beside the Overview Report module. The side pane and the tab read IsRunning and draw from its events, so they keep no copies of their own. The patch windows can ask it.

Wins

  • Locality: one running fact
  • Deletes SetScanning and the ctor flag
  • #131 gets a seam to decide at
  • Scan Game rule testable without MainWindow
  • Leverage: three readers, one interface

Open in grilling: #131 is needs-triage. This candidate places the seam. It does not choose wait, refuse or mark stale. The rival design puts a “writes game files” exclusive tag on runtime.Actions, which every Operation already passes through. One tag would cover the Scan, both Patch Alls and the Downgrader’s download poll.

Hidden assumption: the _tree! in OnStarted is safe only because the side pane alone starts a Scan. A session-level module would make that a crash path.

Naming: the glossary’s Scan is ScanState.StartAsync, but Core’s Scan is only the part after the refresh. Also, ScanSettings is the Scan’s whole input, not a Scan Setting. Settle the names while deepening.

Solution

Two adapters, WindowHost and DowngraderRunTests.ScriptedHost, make this a real seam. ADR-0009 keeps the close guard driven by QueueRunning outside the runner, and this candidate leaves that alone.

Let the Overview Report own its problems and verdicts

Worth exploring in-process carried over from 10-31
  • Core/Overview/OverviewReport.cs (shared lists :123–124, call order :130–175, AddSimple :180)
  • Core/Overview/OverviewModules.cs (6 append sites) · OverviewArchives.cs (4)
  • Core/Scanner/Scan.cs :249 (borrows OverviewReport.AddSimple)
  • App/Tabs/OverviewTab.cs (Win11 rule :236, AtMost :665, ModManagerDetails :126, colours :477 :596 :617)

Before: 16 appends, two logging rules

After: Gather orders, logs and judges

Problem

Three gatherings append to one shared list at 16 sites. Eight of the appends log and eight don’t. The problem order exists only as call order. The MO2 Windows 11 verdict is decided in the tab and tested only by finding a control.

Solution

Each gathering returns its problems. Gather owns the order and the log line. The tab’s MO2 and OS verdicts become fields of the report.

Wins

  • Locality: problem order in one method
  • One logging rule, not two
  • Win11 verdict gets unit tests
  • Scan stops borrowing AddSimple
Under ADR-0008 a change to problem order or log lines is accepted by re-recording the goldens and reviewing the diff. The goldens show the order, which makes this a cheap change to check.

Let the tab host build a page after a late success

Speculative in-process #104
  • App/Tabs/TabPage.cs :34–43 (LoadAsync and BuildContent each “called at most once”)
  • App/Tabs/LazyTab.cs :59–63, :78–97 (never retries)
  • App/Tabs/OverviewTab.cs :148–179 (throws on a failed load; subscribes to Refreshed only after build)
  • App/ViewModels/OverviewState.cs :150–164 (already makes a later report current)
  • tests: LazyTabTests.cs :158 · OverviewTabFailureTests.cs :188–205 (pin today's behaviour)

Before: two load states, one can't go back

OverviewState has a good report; LazyTab still shows the loading text.

After: the host owns the late build

Problem

OverviewState makes a later report current. LazyTab, though, keeps its own one-way “load failed” state, so the Overview tab stays on its loading text.

Solution

A page can tell the host it is now ready, and LazyTab owns the late build. The Overview tab raises that ready signal from the Overview Report module’s Refreshed.

Wins

  • #104 fixed in the host
  • Locality: load state in one module
Only the Overview tab needs a late load today. The F4SE and Scanner loads don’t depend on a later refresh. One page makes this a hypothetical seam, and a narrow fix inside OverviewTab is the alternative to weigh.
